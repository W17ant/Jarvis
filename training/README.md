# Training — LoRA fine-tuning for Jarvis tool routing

The local `qwen2.5:7b` model frequently fails to dispatch tools — it answers from training data instead of calling `request_browse`, `open_app`, `show_news_panel`, etc. The system-prompt directives in `bridge/server.mjs` help; this directory takes the next step by training a LoRA adapter on top of Qwen 2.5 that biases the model toward correct tool dispatch.

## What's in here

```
training/
├── data/
│   ├── tool-routing-seed.jsonl       ← 30 hand-curated examples (start here)
│   └── expansion-candidates.jsonl    ← generated by expand_dataset.py from real bridge log
├── scripts/
│   ├── eval.py                       ← measure tool-routing accuracy against the live bridge
│   └── expand_dataset.py             ← mine /tmp/jarvis-bridge.log for failure cases
└── README.md                         ← you are here
```

## When to actually train

**Don't, if you're switching to cloud LLM.** Claude Sonnet 4.6 or GPT-4o via the bridge's existing provider plumbing (`bridge/llm/providers.mjs`) gives better tool-routing than any local 7B + LoRA combination. Set `ANTHROPIC_API_KEY` + `LLM_PROVIDER_DEFAULT=anthropic` and skip this directory entirely.

**Do, if** you want fully-local operation AND have observed that the system-prompt bias + fast-path layer aren't enough on their own. A LoRA adapter trained on ~200-500 real Jarvis tool-routing examples will close most of the remaining gap on Qwen 2.5 7B.

## Workflow

### Step 1 — measure current baseline

Make sure the bridge is running, then:

```bash
python3 scripts/eval.py
```

This prints pass/fail per case and an overall percentage. Note this baseline. You'll compare against it after training.

### Step 2 — grow the dataset

The 30 seed examples cover the common shapes but won't move the needle on their own. Mine real failures from the live bridge log:

```bash
python3 scripts/expand_dataset.py --only-failures
```

This writes `data/expansion-candidates.jsonl` with every passive query that resulted in zero tool calls. Open the file, label each row's `tool_calls` field with the correct dispatch (or leave empty if the model was right to answer conversationally), then append the curated rows to `tool-routing-seed.jsonl`.

Aim for 200-500 labelled examples before training. Less than that and the LoRA won't generalise.

### Step 3 — train with MLX

[MLX](https://github.com/ml-explore/mlx-examples/tree/main/lora) is Apple's native ML framework — runs LoRA fine-tuning straight on Apple Silicon GPU. Already in your stack via `mlx-whisper`.

Install the trainer if you haven't:

```bash
pip install mlx-lm
```

Convert the JSONL dataset to MLX format (chat template applied per model):

```bash
mkdir -p data/mlx
# MLX expects {train,valid,test}.jsonl files. Split 80/10/10:
python3 -c "
import json, random
random.seed(42)
rows = [json.loads(l) for l in open('data/tool-routing-seed.jsonl')]
random.shuffle(rows)
n = len(rows)
splits = {'train': rows[:int(n*0.8)], 'valid': rows[int(n*0.8):int(n*0.9)], 'test': rows[int(n*0.9):]}
for k, v in splits.items():
    with open(f'data/mlx/{k}.jsonl', 'w') as f:
        for r in v: f.write(json.dumps(r) + '\n')
print({k: len(v) for k, v in splits.items()})
"
```

Run the training:

```bash
python3 -m mlx_lm.lora \
  --model mlx-community/Qwen2.5-7B-Instruct-4bit \
  --train \
  --data data/mlx \
  --iters 1000 \
  --batch-size 1 \
  --lora-layers 16 \
  --adapter-path adapters/jarvis-tool-routing
```

On M1 Max 64GB this runs at roughly 1-2 iters/sec for the 4-bit Qwen2.5-7B base. 1000 iters ≈ 10-20 minutes. The adapter weights end up in `adapters/jarvis-tool-routing/` at ~50MB.

### Step 4 — serve the adapter via Ollama

Ollama doesn't yet have first-class MLX adapter loading. Options:

**A — Convert + import via llama.cpp / GGUF.** Fuse the adapter into the base model, export as GGUF, load with Ollama's `Modelfile` `FROM` directive. ~20 mins, well-documented in MLX repo.

**B — Run the model under MLX directly.** Replace the Ollama call site in `bridge/llm/providers.mjs` with a thin wrapper around `mlx_lm.generate` or `mlx_lm.server`. Closer to bare metal, no GGUF round-trip, but loses Ollama's keep-alive + concurrency primitives — you'd be rebuilding those.

A is the lower-friction path for now. B is the right long-term answer if local LLM stays in the stack.

### Step 5 — re-measure

```bash
python3 scripts/eval.py
```

Compare against the baseline from Step 1. A useful LoRA should lift tool-routing accuracy from ~50-60% to 85-95% on the eval set. If it doesn't, the dataset is probably too small or imbalanced — go back to Step 2 and label more.

## Notes on the dataset format

Each line is a JSON object with a `messages` array in the OpenAI / Anthropic chat shape. The training script reads three roles: `system`, `user`, and `assistant`. The assistant turn may include a `tool_calls` array (same shape as OpenAI's tool-use API):

```json
{
  "messages": [
    {"role": "system", "content": "You are Jarvis..."},
    {"role": "user", "content": "find me a cafe near the beach"},
    {"role": "assistant", "content": "", "tool_calls": [
      {"name": "open_url", "arguments": {"url": "https://www.google.com/maps/search/cafe%20near%20the%20beach"}}
    ]}
  ]
}
```

Conversational examples (where the right answer is NOT a tool call) have a plain text `content` and no `tool_calls`. The 50/50 mix of tool-call and conversational examples is intentional — without negatives, the LoRA overfits to "always call a tool", which breaks small talk.

## Why not just use a bigger model

You should. Qwen 2.5 14B on your M1 Max 64GB (your hardware's recommended tier — see `tools/setup-wizard.mjs`) almost certainly gets you to 80%+ tool routing without any LoRA training. The LoRA is the path of last resort when:

1. You need 7B speed and can't afford 14B's tokens/sec
2. The system-prompt bias alone hasn't moved the needle far enough
3. You want a kiosk that ships with a model you control end-to-end

If none of those apply, run `ollama pull qwen2.5:14b`, update the model in your bridge config, and skip this whole directory.
