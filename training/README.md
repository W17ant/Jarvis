# Training — LoRA fine-tuning for Jarvis tool routing

Local `qwen2.5:7b` frequently answers from training data when it should be calling a tool (`request_browse`, `open_app`, `show_news_panel`, etc.). The system-prompt directives in `bridge/server.mjs` and the fast-path layer in `bridge/fast-path.mjs` catch most of this. The LoRA in this directory closes the long tail — the queries that *should* hit the LLM and *should* produce a tool call, where the 7b base model still defaults to prose.

## What's in here

```
training/
├── data/
│   ├── tool-routing-seed.jsonl       30 hand-curated (query → expected tool_call) examples
│   └── expansion-candidates.jsonl    generated by expand_dataset.py from /tmp/jarvis-bridge.log
├── scripts/
│   ├── train.sh                      end-to-end LoRA training (MLX on Apple Silicon)
│   ├── serve.sh                      start mlx-lm.server with the fused model
│   ├── eval.py                       measure tool-routing accuracy against the live bridge
│   └── expand_dataset.py             mine the bridge log for failure cases to hand-label
├── output/                           created by train.sh; adapters + fused model land here
└── .venv/                            created by train.sh; mlx-lm + deps
```

## Full workflow

### 1. Baseline

Bridge must be running. Measure where you are now:

```bash
python3 scripts/eval.py
```

You'll see something like `15/30 (50%)`. Note it.

### 2. Grow the dataset

The 30 seed examples are a starting point, not enough on their own. Mine real failures from your bridge log:

```bash
python3 scripts/expand_dataset.py --only-failures
```

That dumps every passive query that hit the LLM with zero tool calls into `data/expansion-candidates.jsonl`. Open it, label each row's `tool_calls` field with the correct dispatch (or leave empty if the model was right to answer conversationally), then append the curated rows to `tool-routing-seed.jsonl`.

Realistic target: 200-500 labelled examples before the LoRA generalises well.

### 3. Train

```bash
./scripts/train.sh
```

Defaults: 1000 iterations, 16 LoRA layers, batch size 1. Override via env vars (`ITERS=2000 LORA_LAYERS=8 ./scripts/train.sh`). First run downloads the 4-bit Qwen2.5-7B-Instruct base (~4.5GB). Training takes 10-20 min on M1 Max for 1000 iters.

Output:
- `output/adapters/qwen2.5-7b-jarvis/` — LoRA adapter only (~50MB, re-trainable)
- `output/qwen2.5-7b-jarvis/` — fused full model (~4.5GB, what mlx-lm.server serves)

### 4. Serve

```bash
./scripts/serve.sh
```

Starts mlx-lm.server on `http://localhost:8081/v1/chat/completions` with the fused model loaded. Leave it running in a terminal (or background with `nohup`/`launchd` later).

### 5. Wire Jarvis to use it

The bridge's provider layer already supports OpenAI-compatible servers via env var (see `bridge/llm/providers.mjs`). Set:

```bash
export OPENAI_API_BASE=http://localhost:8081/v1/chat/completions
export OPENAI_API_KEY=mlx-local          # any non-empty string; mlx-lm.server doesn't check
export LLM_PROVIDER_DEFAULT=openai
./launch.sh restart
```

Or persist in your shell profile / `.env`.

### 6. Re-measure

```bash
python3 scripts/eval.py
```

Compare against the baseline from step 1. A useful LoRA should lift tool routing from ~50% to 85-95% on the eval set. If it doesn't, the dataset is too small or imbalanced — expand and retrain.

## Honest trade-offs

**The cheapest improvement is still the system prompt + fast-path work that ships separately** (`bridge/server.mjs` + `bridge/fast-path.mjs`). That's free and applies to any backend. Measure baseline with those already in place before deciding the LoRA is worth the labelling effort.

**Cloud Anthropic is genuinely better than local-LoRA-on-7b** if you're OK with the trade-off:
- Internet dependency, ongoing token cost
- ~$3/M tokens for Claude Sonnet 4.6
- Much higher quality on tool routing than any 7B model can reach
- Zero training effort
- Set `ANTHROPIC_API_KEY` + `LLM_PROVIDER_DEFAULT=anthropic` and skip this entire directory

**The LoRA is the right answer when** you want fully-local operation, can't move to 14b (RAM/GPU constraints), and have collected the real-world failures to train against. That's a legitimate set of constraints — Jarvis is designed for it.

## Dataset format

JSONL, one example per line. Each line is a `{"messages": [...]}` object in the OpenAI chat format. Assistant turns may include a `tool_calls` array (OpenAI tool-use shape):

```json
{
  "messages": [
    {"role": "system", "content": "You are Jarvis..."},
    {"role": "user", "content": "find me a cafe near the beach"},
    {"role": "assistant", "content": "", "tool_calls": [
      {"name": "open_url", "arguments": {"url": "https://www.google.com/maps/search/cafe%20near%20the%20beach"}}
    ]}
  ]
}
```

Conversational examples have plain text `content` and no `tool_calls`. The 50/50 mix of tool-call and conversational examples in the seed is intentional — without negatives, the LoRA overfits to "always call a tool" and breaks small talk.

## Switching back to vanilla Ollama

```bash
unset OPENAI_API_BASE LLM_PROVIDER_DEFAULT
./launch.sh restart
```

Bridge falls back to ollama → qwen2.5:7b base model. LoRA-tuned model still sits at `output/qwen2.5-7b-jarvis/` for next time.
